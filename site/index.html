02 / EVIDENCE, NOT ASSUMPTION

“做完了”，
要有依据。

让检查与它实际覆盖的代码版本绑定。让交付不仅有代码，也有解释和证据。

理解验证规则 ↗
01

PASS 绑定检查前的提交

源码在检查后发生变化，写锚就会拒绝。报告提交限定路径，避免夹带未经验证的源码。

02

复选框不能独立放行

完成状态读取已提交的 checkpoint 标签；零用例、缺证据、环境故障都不能被包装成真实通过。

03

保留起点，尊重合并意图

每个 change 保存固定起始 SHA 与工作分支。默认不合并；只有你明确指定目标，才执行合并。

04

承认检查的边界

内联多视角共享一个上下文。gate 能校验结构与内容关系，不能证明语义判断无误，也不能代替真实测试。

从你的项目，开始。

01

安装工具链

需要 Git、Bash、Python 3、OpenSpec CLI（按使用手册安装验证版本，需 Node.js ≥ 22.20）和 mikefarah/yq。GitHub 仓库访问需要对应权限。

02

接入目标项目

在你的业务项目中调用 /g-init，它会铺好 openspec/ 骨架，无需先跑 openspec init。补充真实技术栈、约束和测试命令。

06 / THINGS WORTH KNOWING

开始之前，你可能想知道。

更多故障排查 ↗
走完整个流程后，会自动合并或推送吗？＋

不会默认合并，也不会自动 push。无论从 a 新建功能分支，还是直接在 a 开发，默认都是提交、验证、归档后留在工作分支。只有你明确指定合并目标，才会尝试 ff-only 合并。

中途换会话，需要从头再来吗？＋

不需要。对同一个 change 重新运行 /g-done，执行者会读取 gate、报告、固定基准和提交记录，定位需要补做的步骤。已写代码但缺验收或完成标签的票，会先核对已有实现，再补齐验证。

多个评审视角，就是多个独立代理吗？＋

不是。当前是一个主会话逐视角检查，不调用子代理，不跨模型调度，也不配置模型档位。不同视角有各自的清单，但共享上下文，不能宣称提供了独立第二意见。

没有自动测试的项目，可以使用吗？＋

可以，但必须如实说明覆盖边界。未配置命令不等于没有测试：执行者先查 CI、README 和既有约定。确实没有某一层才记录依据；有明确测试域且配置无自动层时，也要保留起始版本与需求验收证据。

为什么还需要我批准设计？＋

范围、偏好和关键取舍最终属于你。主变更链保留设计批准点，AI 准备推荐、依据、代价与备选；明确批准后才记录设计门。报告写着通过或者你没有反对，都不能替代明确批准。

我需要记住全部 12 个命令吗？＋

不用。日常主线是 /g-init、/g-spec、/g-review spec 和 /g-done。出票、逐票实现与代码审通常由 done 按 gate 调用；其余入口在需要规划、环境、记录或复盘时使用。
